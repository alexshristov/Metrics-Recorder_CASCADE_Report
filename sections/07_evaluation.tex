The answer the question on how CASCADE performs for different LLMs, we ran our extended version of CASCADE on the core dataset, being the 72 pairs of inconsistent and consistent code-documentation samples, of the original paper.
The LLMs we used for this experiments were gpt-oss:20b\cite{ollama_gpt_oss_20b}, mistral-small3.2:latest\cite{ollama_mistral-small3.2_24b} and qwen2.5-coder:14b-instruct\cite{ollama_qwen2.5-coder-14b-instruct}, which we hosted on a local setup.\footnote{
\textbf{Hosting Environment:} Experiments ran on a desktop machine with Windows 11, a Ryzen 9 7900X 12-Core CPU, 64GB RAM, and a Radeon RX 7900 XT (20GB VRAM, being throttled to a maximum frequency of 1600 MHz for heat reasons) using ollama (0.21.1) to host the specified models.}
Additionally we used an externally hosted LLM: Qwen3-Coder-Next-FP8\cite{qwen_qwen3_coder_next_tech_report}, which was hosted by our university.
The external LLM is meant to demonstrate a trade-off between having access to stronger hardware and thus larger models, but having to share that access with many other people.

For each LLM, we measured the result of the CASCADE program, as well as the output of our MetricsRecorder. From the output metrics, we focus on the average execution time and the average LLM-token usage over all datapoints.

The experiments produced a lot of data, we try to condense it down to a few insightful tables, though for a complete overview the results can be viewed independently\footnote{The data is available at \url{https://box.hu-berlin.de/f/d31a0c543946447a89dd/}}.

Table \ref{tab:results} shows the original metrics (Precision, Recall, etc.) on the different models.
We can immediately notice, that the recall is much lower than for the original CASCADE run (0.21) for all of the LLMs.
This is because in our runs, the LLMs rarely reported an Inconsistency.
Also the precision values are a bit lower than in original Paper (where it was 0.88).
From these values the gpt-oss model is the best regarding recall and shares the highest precision value with the qwen2.5-coder model

Table \ref{tab:resources} shows the most important metrics we recorded using the introduced MetricsRecorder.
The samples are split into multiple groups for each model. 
The TP, FP, TN and FN groups correspond to the samples that returned True-Positives, False-Positives and so on.
The eTN and eFN are error-corrected groups.
They are subsets of TN and FN respectively, where CASCADE did not respond NoInco because all the tests passed, but rather because of any errors during the Pipeline.
An error occuring can mean many things, but during the run we mostly found errors to occur because of either
1. timeouts during an LLM api-call (>1min), or 2. the LLM did not understand how to use the tools provided to fix compiler errors, leading to a failed code extraction from the answer.
The ERR category includes all error-results.
The data shows, that mistral-small had the lowest average token usage, while qwen2.5-coder had the lowest average execution time.
We can also see that the LLMs make many mistakes, with gpt-oss having the lowest error count of 94 errors ($\sim$66\% of samples).
The high error rate lowers the recall rate by reducing the amount of samples, on which CASCADE can effectively operate.
